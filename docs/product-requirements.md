# プロダクト要求定義書 (Product Requirements Document)

## プロダクト概要

### 名称
**モールスシンク(morse-sync)** - QRコードを読むだけで、みんなのスマホが揃ってモールス信号を光らせるWebサービス

### プロダクトコンセプト
- **QRコードを読んでタップするだけ**: インストール・登録・許可なしで、数秒で参加できる
- **サーバーなしで揃う**: 各端末の時計を基準に開始時刻を計算するので、端末同士やサーバーとの通信なしに何台でも同期する
- **設定はURLに全部入る**: メッセージ・速さ・色をURLに収め、QRコードやメッセージアプリで配るだけで全員が同じ設定になる

### プロダクトビジョン
その場に居合わせた人たちが、QRコードを1回読むだけで同じモールス信号を一斉に光らせられる世界を目指す。
参加者にアプリのインストールやカメラの許可を求めず、iPhoneでもAndroidでも同じ手順で参加できるようにする。
まず誰の端末でも確実に動く「画面点滅」で同期の仕組みを完成させ、その上に本命である「カメラのフラッシュ(トーチ)での点滅」を載せる。
静的ファイルだけで完結させ、GitHub Pagesに置くだけで誰でも公開・運用できるものにする。

### 提供する価値
- **参加のハードルを下げる**: 参加者の操作は「QRを読む → 1回タップ」の2ステップのみ
- **設定の伝達ミスをなくす**: 口頭で伝えていたメッセージ・開始タイミング・速さ・色を、QRコード1つで正確に配布
- **モールスの知識を不要にする**: 文字→符号の変換、短点・長点・間隔のタイミング計算をすべて自動化
- **運用コストゼロ**: サーバー不要、GitHub Pagesの無料枠で公開できる

### 目的
- 複数台のスマホを、通信なしで目視上ずれを感じない精度で同時に点滅させる
- 主催者が1分以内に点滅パターンを作り、QRコードで配布できるようにする
- 画面点滅で確立した同期の仕組みを、フラッシュ(トーチ)点滅に展開する

  1. 事前に自宅でメッセージと色を決め、所要時間を確認する
  2. 当日、会場で自分のスマホにQRコードを表示して参加者に見せる
  3. 参加者全員が点滅を始めたら、自分も参加して一緒に光らせる

  - カメラなど、目的のよく分からない許可を求められると不安になる

  1. 主催者のQRコードを標準カメラで読み取る
  2. 開いたページの「タップして参加」を押す
  3. 必要に応じて画面の明るさを最大にし、スマホを掲げる

## 成功指標(KPI)

本プロダクトは個人開発のOSSであり、アクセス解析は導入しない(後述のプライバシー方針)。そのため指標は、公開前後に行う実機検証とユーザーテストで測定する。

### プライマリーKPI
- **同期精度**: 異なる機種・OSを混在させた5台以上で、各点滅の開始時刻のずれが最大100ms以内(MVP公開時)
  - 測定方法: 全端末を並べて240fpsのスロー動画で撮影し、フレーム数から点灯開始のずれを計測。連続する20回以上の点灯で評価する
  - 前提: 各端末の時刻が自動設定(ネットワーク時刻)になっていること
- **参加のしやすさ**: 初見の参加者5人以上のうち全員が、口頭の説明なしでQR読み取りから点滅開始の待機状態まで到達できる(MVP公開時)
  - 測定方法: 説明なしのユーザーテストで、QRを読んでから「待機中」表示に到達するまでの操作を観察
- **参加までの時間**: QRを読み取ってから「待機中」表示までの時間が、4G回線で10秒以内(MVP公開時)

### セカンダリーKPI
- **動作環境カバー率**: 下記「動作環境」の全ブラウザで画面点滅が動作する(MVP公開時)
- **パターン作成時間**: 初見の主催者が、メッセージ入力からQRコード表示まで1分以内に完了できる(MVP公開時、ユーザーテスト3人以上)
- **フラッシュ同期**: フラッシュ対応端末で、フラッシュの点灯が同じ端末の画面点滅に対して最大150ms以内で追従する(P1機能リリース時、スロー動画で測定)

### 画面構成

同じURLで、`#` の後ろの設定(以下「ハッシュ」)の有無によって2つの画面を切り替える。

| 画面 | 表示条件 | 主な利用者 |
|------|---------|----------|
| 作成画面 | ハッシュなしで開いたとき | 主催者 |
| 参加画面 | 有効な設定入りのハッシュ付きで開いたとき | 参加者(主催者自身も参加可) |

- 作成画面から「このパターンで参加」ボタンで参加画面に移れる
- 参加画面から「パターンを作る」リンクで作成画面に戻れる

### コア機能(MVP)

#### 1. 点滅パターンの作成

**ユーザーストーリー**:
主催者として、モールス信号の知識がなくてもイベント用の点滅パターンを作るために、メッセージを入力するだけで符号と所要時間が分かる作成画面が欲しい

**設定項目**:

| 項目 | 入力方法 | 既定値 | 許容範囲 |
|------|---------|-------|---------|
| メッセージ | テキスト入力 | `SOS` | 欧文の対応文字のみ、1〜50文字 |
| 1拍の長さ | 数値入力(ミリ秒) | 250ms | 200〜2000ms |
| 点灯色 | カラーピッカー、または16進の入力欄 | `#ffcc00` | 任意のRGB色(16進6桁) |

- 1拍の下限200msは、画面の更新間隔や端末間の時計の微差を吸収するため、および光過敏への配慮(後述)による

**対応文字(欧文)**:
- 英字 A〜Z(小文字は大文字として扱う)
- 数字 0〜9
- 記号 `. , ? ' ! / ( ) & : ; = + - _ " $ @`
  - 符号はITU-R M.1677-1に従う。同勧告に定めのない `! & ; _ $` は、アマチュア無線で広く使われている慣用の符号を使う(対応表は機能設計書の付録)
- 空白(単語の区切り)

**受け入れ条件**:
- [ ] メッセージ入力中、入力内容に対応するモールス符号(`・` と `−`)がリアルタイムに表示される
- [ ] 1周分の所要時間(秒、小数第1位まで)が入力のたびに更新表示される
- [ ] 同期の周期はユーザーが入力・選択する項目ではなく、画面にも表示されない(内部で自動決定し、URLにのみ含める)
- [ ] 所要時間が60秒を超える場合、「60秒以内に収まりません。メッセージを短くするか、1拍を短くしてください」と表示され、QRコードは生成されない
- [ ] 対応外の文字(日本語、絵文字など)を含む場合、該当文字を強調表示し「この文字は送れません: あ」とQRコード生成前に表示される。QRコードは生成されない
- [ ] 1拍の長さに許容範囲外の値を入れると、エラーが表示されQRコードは生成されない
- [ ] 点灯色はカラーピッカーと16進の入力欄(`#006eff` 形式)のどちらからでも設定でき、一方を変えるともう一方に反映される
- [ ] 16進の入力欄が6桁の16進でないときは「点灯色は #ffcc00 のように6桁で入力してください」と表示され、QRコードは生成されない

**優先度**: P0(必須)

#### 2. QRコードでの設定共有

**ユーザーストーリー**:
主催者として、その場で参加者全員に同じ設定を正確に配るために、設定入りのQRコードと共有用URLが欲しい

参加者として、後から来た隣の人にもすぐ参加してもらうために、点滅に参加している自分のスマホからも同じQRコードを見せたい

**受け入れ条件**:
- [ ] 入力内容が有効な場合、設定をすべて含むURLが生成され、そのURLのQRコードが作成画面に表示される
- [ ] QRコードの生成はブラウザ内で行われ、生成のための外部通信は発生しない
- [ ] QRコードを画面いっぱいに拡大表示するボタンがあり、拡大表示中は白背景・十分な余白(クワイエットゾーン)付きで表示される
- [ ] 下記URL例(メッセージ`HELLO`)で生成したQRコードを、主催者のスマホ画面に表示した状態で、1m離れた位置からiPhone・Androidの標準カメラで読み取れる
- [ ] 「共有」ボタンを押すと、Web Share API対応端末ではOSの共有シートが開き、非対応端末ではURLがクリップボードにコピーされ「コピーしました」と表示される
- [ ] 設定を変更するとURLとQRコードが即座に更新される
- [ ] 参加画面からも、参加中の設定と同じURLのQRコードを表示できる(操作は機能4の「点滅中のメニュー」から)
- [ ] 参加画面のQRコード表示中も「共有」ボタンが使える
- [ ] 参加画面で表示したQRコードを読み取った端末は、元のQRコードを読み取った端末と同じタイミングで点滅する(設定がすべてURLに入っているため、何人経由で広がっても同じ)

**URLの形式(仕様バージョン1)**:

```
https://nogawa-asase.github.io/morse-sync/#v=1&l=en&m=HELLO&p=15&u=250&c=ffcc00
```

| キー | 内容 | 必須 | 省略時 | 例 |
|-----|------|-----|-------|-----|
| v | 仕様バージョン | 必須 | - | `1` |
| l | 文字の種類 | 任意 | `en` | `en`(将来 `ja`) |
| m | メッセージ(URLエンコード) | 必須 | - | `HELLO` |
| p | 同期の周期(秒)。内部で自動決定した値を入れる(ユーザーは意識しない) | 必須 | - | `15` |
| u | 1拍の長さ(ミリ秒) | 任意 | `250` | `250` |
| c | 点灯色(16進数6桁、`#`なし) | 任意 | `ffcc00` | `ffcc00` |

- 設定は `?` ではなく `#` の後ろに入れる(再読み込みなしで書き換えられ、設定内容がサーバーのアクセスログに残らない)
- キーは1文字にしてURLを短く保ち、QRコードの模様を粗くして離れた位置から読み取りやすくする

**優先度**: P0(必須)

#### 3. 設定URLの読み込み

**ユーザーストーリー**:
参加者として、何も入力せずに主催者と同じ設定で参加するために、QRコードを読むだけで設定が反映されてほしい

**受け入れ条件**:
- [ ] 有効なハッシュ付きURLを開くと参加画面が表示され、メッセージと1拍の長さが画面に表示される(同期の周期は表示しない)
- [ ] 任意項目(`l`, `u`, `c`)を省略したURLでも、既定値で正しく動作する
- [ ] `v` が未知のバージョン(例: `v=2`)の場合、「このQRコードは新しいバージョン用です。ページを再読み込みしてください」と表示する
- [ ] 参加側は `p` の値をそのまま使い、自分で周期を計算し直さない(作成画面と参加画面で計算方法が変わっても、全員が同じ周期で動くようにするため)
- [ ] `p` が60の約数でない場合、または1周分の所要時間より短い場合は、範囲外の値として扱う
- [ ] 必須項目の欠落・範囲外の値・対応外の文字を含む場合、点滅は開始せず「QRコードの内容が正しくありません」と表示し、作成画面へのリンクを出す
- [ ] ページを開いたままハッシュが変わった場合(同じページで別のURLを開いた場合など)、新しい設定が反映される

**優先度**: P0(必須)

#### 4. 参加開始の操作

**ユーザーストーリー**:
参加者として、迷わず点滅に参加するために、1回タップするだけで点滅の準備がすべて整ってほしい

**受け入れ条件**:
- [ ] 参加画面に「タップして参加」ボタンが大きく表示される(ボタンの高さ・幅は画面の短辺の30%以上)
- [ ] タップすると、Wake Lock APIによるスリープ防止が有効になる
- [ ] タップすると、Fullscreen APIに対応したブラウザではフルスクリーン表示になる(非対応のiPhone Safariなどでは通常表示のまま動作を続ける)
- [ ] 「必要に応じて、画面の明るさを最大にしてください」という案内が表示される(ブラウザからは輝度を変更できないため)
- [ ] 次の開始時刻までの残り秒数がカウントダウン表示される(待機中)
- [ ] 標準の画面点滅では、カメラ・マイク・位置情報・通知など、ブラウザの許可ダイアログが一切表示されない
- [ ] 待機中・点滅中に画面をタップすると、点滅を続けたまま画面下部にメニューが表示される
  - メニューの項目: 「QRコードを見せる」「一時停止」(P1のフラッシュ機能の実装後は「フラッシュ」も)
  - 5秒間操作がないとき、またはメニューの外側をタップしたときは、メニューを閉じて点滅をそのまま続ける(うっかり触っても止まらないようにするため)
- [ ] 「QRコードを見せる」を選ぶと、点滅を止め、白背景にQRコードを画面いっぱいに表示する(点滅する背景の上では相手のカメラが読み取りにくいため)
- [ ] QRコード表示中は、スリープ防止とフルスクリーン表示を維持する
- [ ] QRコード表示中に「戻る」を押すと点滅画面に戻り、次の開始時刻から周りの端末と揃って再開する(再参加の操作は不要)
- [ ] 「一時停止」を選ぶと消灯して「再開」ボタンを表示し、「再開」を押すと次の開始時刻から再開する
- [ ] Wake Lockが解除された後(タブ切り替え・画面オフ)にページへ戻ると、自動でWake Lockを再取得し、点滅を再開する
- [ ] Wake Lock非対応のブラウザでは「画面が自動で消えないよう、端末の設定を確認してください」と案内を表示し、点滅自体は継続する

**優先度**: P0(必須)

#### 5. 時刻同期による画面点滅

**ユーザーストーリー**:
参加者として、周りの人と揃って光るために、何もしなくても他の端末と同じタイミングで画面が点滅してほしい

**同期の仕組み**:
- 開始時刻 = 端末の現在時刻(UNIX時刻)を同期の周期で割り切れる時刻のうち、次に来るもの
  - 例: 周期15秒なら毎分0秒・15秒・30秒・45秒に1周分のメッセージを開始する
- 点灯/消灯の判定は「開始時刻から何ミリ秒経過したか」を毎フレーム現在時刻から計算して決める(前回の切り替えからの経過時間を積み重ねないため、誤差が蓄積しない)
- サーバーや端末同士の通信は使わない

**同期の周期の自動決定(ユーザーには見せない内部仕様)**:
- 繰り返しの間の消灯時間をできるだけ短くするため、同期の周期は「1周分の所要時間」以上となる60の約数のうち、最も短いものを自動で選ぶ
- 1周分の所要時間 = メッセージを送る時間 + 繰り返しの区切りとなる単語間の間隔(7拍)
  - 末尾に単語間の間隔を含めることで、次の周の先頭と前の周の末尾が続けて読まれないようにする
- 60の約数に限る理由: 周期が60を割り切るため、毎分0秒がどの周期でも必ず開始時刻になり、端末の時計だけで開始時刻を揃えられる
- 例: `SOS`(1拍250ms)は送信に27拍 + 区切り7拍 = 34拍 = 8.5秒 → 周期10秒(消灯のまま待つ時間は1.5秒)
- 所要時間が60秒を超える場合は周期を決められないため、QRコードを生成しない(作成画面では「60秒以内に収まりません」とだけ表示する)
- 自動決定の境界例: 所要時間8.5秒 → 10秒、10.0秒 → 10秒、10.1秒 → 12秒

**モールスのタイミング(ITU-R M.1677準拠)**:

| 要素 | 長さ | 状態 |
|------|-----|------|
| 短点(・) | 1拍 | 点灯 |
| 長点(−) | 3拍 | 点灯 |
| 符号内の間隔 | 1拍 | 消灯 |
| 文字間の間隔 | 3拍 | 消灯 |
| 単語間の間隔 | 7拍 | 消灯 |

**受け入れ条件**:
- [ ] 点灯中は画面全体(ボタン・文字を含まない)が点灯色、消灯中は黒(`#000000`)で表示される
- [ ] 1周分を送り終えたら、次の開始時刻まで消灯したまま待機し、次の開始時刻から再び送る
- [ ] 周期の途中で参加した場合は、次の開始時刻から送り始める
- [ ] 各点灯・消灯の切り替えが、計算上の時刻に対して1フレーム(60Hz端末で約17ms)以内のずれで行われる
- [ ] 1時間連続で点滅させても、1周目と最終周の開始時刻のずれ(計算上の時刻との差)が増加しない
- [ ] 点滅中、ネットワーク通信が一切発生しない(ブラウザの開発者ツールで確認)
- [ ] 点滅中に画面上部に小さく現在送信中の文字が表示される(表示の有無は切り替え可能、既定は表示)

**優先度**: P0(必須)

### 重要機能

#### 6. フラッシュ(トーチ)での点滅 【本命】

このサービスで最も大事にしたい機能。P1としているのは、画面点滅(P0)で同期の仕組みを完成させてから載せるという実装順の都合であり、重要度が低いわけではない。

**ユーザーストーリー**:
参加者として、暗い会場でより遠くまで届く強い光を出すために、画面点滅と揃ってスマホのフラッシュを点滅させたい

**受け入れ条件**:
- [ ] 参加画面に「フラッシュも使う」オプションボタンが表示される(既定はオフ)
- [ ] ボタンの近くに「フラッシュを使うためにカメラの許可が必要です。撮影・録画はしません」と表示される
- [ ] ボタンを押したときに初めてカメラの許可を求める(ページを開いた時点では求めない)
- [ ] 許可後、画面点滅と同じタイミング計算でフラッシュの点灯/消灯が切り替わる
- [ ] 取得したカメラ映像は画面に表示せず、保存・送信もしない
- [ ] トーチに対応していない端末・ブラウザでは、ボタンを無効表示にし「この端末ではフラッシュを使えません」と表示する
- [ ] カメラの許可を拒否された場合も、画面点滅は継続する
- [ ] フラッシュ利用時、1拍の長さが250ms未満なら「フラッシュは切り替えが遅れることがあるため、1拍250ミリ秒以上をおすすめします」と表示する(※当初300msとしていたが、2026-09-25にiOS 26.5で250msでも画面とそろうことを確認して変更。Androidで遅れが大きければ見直す)

**優先度**: P1(重要)

#### 7. オフライン対応(PWA)

**ユーザーストーリー**:
参加者として、電波の悪い会場でも参加できるように、一度開いたページは圏外でも開けるようにしてほしい

**受け入れ条件**:
- [ ] 一度ページを開くと、Service Workerによりページ一式が端末に保存される
- [ ] 保存後は機内モードでも、設定入りのURL(QRコード)を開いて参加・点滅できる
- [ ] 保存後は機内モードでも、作成画面でパターン作成とQRコード表示ができる
- [ ] ページを更新した場合、次回オンラインでアクセスしたときに新しい版に切り替わる

**優先度**: P1(重要)

#### 8. 和文モールス対応

**ユーザーストーリー**:
日本語話者の主催者として、日本語のメッセージを送るために、ひらがな・カタカナをモールス信号にしたい

**受け入れ条件**:
- [ ] 作成画面で文字の種類(欧文/和文)を切り替えられ、和文ではURLに `l=ja` が入る
- [ ] ひらがな・カタカナ・長音符・句読点を和文モールス符号に変換できる
- [ ] 濁点・半濁点は独立した符号として送る(例: 「ガ」→「カ」+濁点)
- [ ] 漢字を入力した場合は「漢字は送れません。ひらがな・カタカナで入力してください」と表示される
- [ ] 変換表の追加のみで対応でき、変換処理のコードは欧文と共通である

**優先度**: P1(重要)

### 将来的な機能(Post-MVP)

#### 9. 音での出力

個人の練習用に、点滅に合わせて音(ビープ音)を出す。複数台での同時使用では端末ごとの音声遅延により二重に聞こえるため、既定はオフとする。

**優先度**: P2(できれば)

#### 10. ワンダーリボンライト連動

サンリオピューロランドのワンダーリボンライトを、スマホから出す高周波音(20kHz前後)で点滅・色変えさせ、モールス信号に合わせて光らせる。1台のスピーカーから届く範囲のライトが同時に光るため、時刻同期が不要になる。制御方式が未解析のため、ブラウザでの画面点滅が完成した後に調査から始める。パーク外で楽しむ前提とする。

**優先度**: P2(できれば)

#### 11. ネイティブアプリ版

ブラウザ版で手応えがあれば、Expoでアプリ化を検討する。画面輝度の最大化、トーチの確実な制御、端末同士の近距離通信での設定共有が可能になる。

**優先度**: P2(できれば)

## 非機能要件

### パフォーマンス
- **ページの転送量**: 初回読み込みの合計転送量が100KB以内(gzip後、QRコード生成ライブラリを含む)
  - 理由: イベント会場で大勢が同時に読み込むと携帯回線が混雑するため
- **表示速度**: 4G回線(Chrome DevToolsの「Fast 4G」相当)で、参加画面の「タップして参加」ボタンが3秒以内に表示される
- **点滅中の通信**: 読み込み完了後、点滅中の通信量はゼロ
- **描画負荷**: 点滅中にフレーム落ち(16.7msを超えるフレーム)が1分あたり5回以下(中級機種、例: iPhone SE 第2世代 / Pixel 6a)
- **配信容量**: GitHub Pagesの帯域上限(月100GB)に対し、1時間1,000アクセスを想定しても十分な余裕がある(100KB × 1,000 = 約100MB/時)

### ユーザビリティ
- **参加操作**: 参加者の操作はQR読み取りとタップの2ステップのみ。名前入力・登録・設定変更は不要
- **許可の最小化**: 標準の画面点滅では、ブラウザの許可ダイアログを一切表示しない
- **表示言語**: 画面の文言は日本語
- **画面サイズ**: 幅320px〜1920pxで、横スクロールなしで操作できる
- **文字サイズ**: 本文は16px以上、主要ボタンのタップ領域は44×44px以上

### 信頼性
- **同期方式**: 端末数が増えても同期の仕組み・精度は変わらない(通信を使わないため)
- **復帰**: タブ切り替えや画面オフから戻った際、自動でスリープ防止を再取得し、次の開始時刻から点滅を再開する
- **誤差の非蓄積**: 点滅のタイミングは毎フレーム現在時刻から計算し、長時間動作させても誤差が蓄積しない
- **時計の前提**: 端末の時刻が自動設定でない場合に大きくずれうることを、参加画面のヘルプに記載する

### セキュリティ・プライバシー
- **データ送信なし**: 入力したメッセージや設定を外部に送信しない。アクセス解析・広告・外部CDNは使用しない(すべて同一オリジンから配信)
- **HTTPS**: GitHub PagesのHTTPSで配信する(Wake Lock・トーチの利用条件)
- **入力の安全な扱い**: URLから読み込んだメッセージは、HTMLとして解釈せずテキストとして表示する(スクリプト注入を防ぐ)
- **カメラの利用範囲**: フラッシュ機能でのみカメラを利用し、映像の表示・保存・送信を行わない

### 安全への配慮
- **光過敏への配慮**: 点滅は1秒あたり3回以下とする(WCAG 2.3.1の基準)。1拍の下限200msでは短点の連続が最大で1秒あたり2.5回となり、この基準を満たす
- **注意書き**: 作成画面と参加画面に「光の点滅に敏感な方はご注意ください」と表示する
- **高周波音(P2)**: 子どもや若い人、ペットに聞こえることがあるため音量は控えめにし、パーク内では使わないよう案内する

### 拡張性
- **仕様バージョン**: URLに最初から仕様バージョン(`v`)と文字の種類(`l`)を持たせ、後から項目を追加しても古いQRコードを正しく読めるようにする
- **変換表の分離**: 文字→符号の対応表をデータとしてプログラム本体から分離し、和文対応は表の追加だけで済むようにする
- **同期の仕組みの共通化**: 点灯/消灯の判定を出力先(画面・フラッシュ・音)から独立させ、出力先を追加しやすくする

## スコープ外

明示的にスコープ外とする項目:
- **サーバー・端末間通信による同期**: 各端末の時計のみで同期する
- **画面輝度の自動変更**: ブラウザからは変更できないため、案内表示で対応する
- **ユーザー登録・ログイン・パターンの保存**: 設定はURLにすべて含まれるため不要
- **アクセス解析・利用状況の収集**
- **ソースコードごとのQRコード配布**: QRの容量(最大3KB弱)が足りない、`data:`形式のURLは最近のブラウザで開けない、HTTPSでないとスリープ防止が使えないため不採用
- **Bluetooth・AirDropでのページ受け渡し**: iPhoneのSafariはWeb Bluetooth非対応、AirDropで受け取ったHTMLはWebページとして動かしにくいため不採用(オフライン対応はPWAで行う)
- **Webアプリでの音による複数台同期**: 端末ごとの音声遅延の差が大きく、二重に聞こえるため
