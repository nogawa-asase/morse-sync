# 要求内容

## 概要

同期の周期を「60の約数」から「メッセージの長さを秒単位で切り上げた値」に変え、繰り返しの間の暗い時間と、途中から参加したときの待ち時間を短くする。

## 背景

- 周期を60の約数(1〜60秒の12通り)から選んでいたため、メッセージの長さが30秒を少しでも超えると周期が60秒になり、毎回30秒近く暗いまま待つことになっていた(ユーザーからの指摘:「寂しい」)
- 開始時刻は「共通の起点(UNIX時刻0)から周期の倍数の時刻」で決めているため、周期が60の約数でなくても全端末で一致する。60の約数に限る理由はなかった(PRDの記述は誤り)

## 実装対象の機能

### 1. 周期の自動決定の変更
- 周期 = 1周分の所要時間(メッセージの長さ)を秒単位で切り上げた値(最小1秒)
- 所要時間が60秒を超える場合は、従来どおりQRコードを生成しない(途中から参加した人の待ち時間を抑えるため、上限は残す)

### 2. URLの周期の検証の変更
- `p` は1〜60の整数で、1周分の所要時間以上なら有効(60の約数でなくてもよい)
- URLの形式(`p` は秒の整数)は変えないため、仕様バージョンは `v=1` のまま。配布済みのQRコード(`p=10`、`p=60` など)は引き続き有効

## 受け入れ条件

- [ ] 所要時間8.5秒(`SOS`) → 周期9秒、14.0秒(`HELLO`) → 14秒、31.2秒 → 32秒、60.0秒 → 60秒、60.1秒 → 生成しない
- [ ] `p=16` のような60の約数でない周期のURLでも、所要時間以上なら参加できる
- [ ] 配布済みのURL(PRDの旧URL例 `p=15` の `HELLO`)が引き続き読み込める
- [ ] `p=0`、`p=61`、小数、所要時間より短い `p` は「QRコードの内容が正しくありません」
- [ ] 周期が60の約数でなくても、同じ時刻には全端末が同じ状態になる(ユニットテストで確認)

## スコープ外

- 周期のミリ秒単位の指定(URLの形式が変わり `v=2` が必要になるため)
- 60秒の上限の撤廃
